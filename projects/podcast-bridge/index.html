00

它是什么

一个供 AI Agent 使用的
全球播客研究 Skill。

podcast-bridge 让 Agent 能用自然语言管理播客订阅、转录与追问节目内容，并把结果保存为可以长期调用的本地知识库。

它不是让 AI 替用户跳过播客，而是把单向收听变成一个可检索、可追问、可比较、可以反复研究的知识过程。

01告诉 Agent直接描述研究问题 02添加 RSS接入不同地区节目 03同步节目标题、日期与简介 04转录定位原文与时间位置 05比较研究跨节目寻找共识 06长期保存Markdown 与索引

产品边界：这里的“全球播客”不是一个预置所有节目的封闭数据库，而是通过开放 RSS 接入不同地区和平台的内容；它不竞争播放体验，解决的是播客如何进入研究工作流。

01

用户需求

用户需求：为什么要做这个产品

在 AI、科技和创业领域，很多最早、最完整的判断会先出现在长播客里，而不是论文、新闻稿或正式文章中。

Amanda Askell 对模型价值与行为的解释、Andrej Karpathy 对 AI 编程和大模型的思考，往往会通过长访谈保留完整的推理过程。对产品经理、研究员、创业者和公司创始人来说，播客已经是一类重要的一手信息源。

但音频天然是线性的：一两个小时听完以后，用户通常只剩下模糊印象，很难定位原文，更难把不同节目、不同嘉宾和不同时间段的讨论连接起来。

02

功能与实现

实现了哪些功能，如何实现

这个 Skill 把订阅管理、内容理解、跨节目研究和长期保存放在同一条工作流里，用户只需要用自然语言提出问题。

例如：“过去一个月，全球播客在 AI 领域主要关注哪些问题？不同嘉宾对 Agent 的判断有什么共识和分歧？”

功能用户得到什么如何实现
管理订阅

用自然语言添加、查看和更新播客源

兼容常见 RSS 结构，同步节目元数据并把订阅清单保存在本地

转录与定位

找到某个概念出现的时间位置和原文

03

取舍

我的取舍

这个版本先验证工作流是否成立，因此我把资源花在“能否稳定完成任务”上，而不是先做完整的独立界面。

01
以 RSS 为入口，不绑定单一平台

原因：开放标准更适合接入不同地区和平台的播客，也让订阅源属于用户。

代价：不同 RSS 的字段与音频地址并不完全一致，需要兼容和回退处理。
02
按需转录，不默认批量处理

原因：先搜索轻量元数据，把时间和算力留给真正值得深挖的内容。

代价：第一次研究某期节目时，需要等待转录完成。
03
先做 Agent Skill，不先做独立 GUI

原因：自然语言已经可以承接订阅、筛选、转录、追问和研究，适合验证完整需求。

代价：使用者需要已有的 Agent 环境。
04
本地 SQLite + Markdown，不先做云知识图谱

原因：资料可搜索、可读、可迁移，也不会在一次对话结束后消失。

代价：跨设备协作和复杂语义关联能力暂时有限。
我真正想验证的，不是“AI 能不能替人听完播客”，而是当播客变成 Agent 可以长期调用的资料后，用户能不能用它持续研究、比较并形成自己的判断。
